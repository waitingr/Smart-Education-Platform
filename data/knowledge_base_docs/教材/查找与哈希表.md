# 查找与哈希表

## 查找的基本概念与平均查找长度

查找是在数据集合中找出关键字等于给定值的元素。评价查找算法效率的核心指标是**平均查找长度 ASL**（Average Search Length），即查找成功或失败时与关键字比较次数的期望：

ASL = Σ pᵢ · cᵢ，其中 pᵢ 是查找第 i 个元素的概率（通常取等概率 1/n），cᵢ 是找到它所需的比较次数。

讨论 ASL 时必须区分「查找成功」与「查找失败」，两者公式不同，考试与工程评估中都常被混淆。

## 顺序查找与折半查找

**顺序查找**从一端逐个比较，ASL 成功 = (n+1)/2，时间 O(n)。对存储结构无要求（顺序、链式均可），适合小规模或无序数据。优化手段：把待查元素放在表头作哨兵，可省去边界判断。

**折半查找（二分查找）**要求**有序 + 顺序存储**。每次与中间元素比较，缩小一半区间，时间 O(log n)，ASL ≈ log₂(n+1) − 1。

二分查找的边界处理是经典易错点，推荐两种写法：

1. 闭区间 `[left, right]`：循环条件 `left <= right`，更新时 `right = mid - 1`、`left = mid + 1`。
2. 左闭右开 `[left, right)`：循环条件 `left < right`，更新时 `right = mid`、`left = mid + 1`。

两种写法不能混用，混用会导致死循环或漏查。求「第一个 ≥ x 的位置」（下界）时用左闭右开更自然：

```
def lower_bound(nums, x):
    left, right = 0, len(nums)
    while left < right:
        mid = (left + right) // 2
        if nums[mid] < x:
            left = mid + 1
        else:
            right = mid
    return left
```

## 分块查找（索引顺序查找）

把表分成若干块，块内无序、块间有序，另建索引表记录每块最大关键字与起始地址。查找时先在索引表中定位块（可用折半），再在块内顺序查找。ASL = 索引查找 + 块内查找，当块长取 √n 时整体最优，约 O(√n)。它是「时间与空间折中」的典型教学案例。

## 二叉排序树与平衡树的查找

BST 的查找从根开始，小于走左、大于走右，比较次数等于路径长度。平均 ASL 为 O(log n)，最坏 O(n)。AVL 树与红黑树通过平衡约束把树高控制在 O(log n)，从而保证最坏情况下的查找效率。

B 树与 B+ 树是多路平衡查找树，专为**磁盘等外存**设计：结点大小对齐磁盘页（如 4KB），一个结点可存几百个关键字，使树高只有 2~4 层，从而把磁盘 IO 次数压到极少。MySQL InnoDB 的索引就是 B+ 树：只有叶子结点存数据（或数据地址），叶子之间用链表相连以支持范围查询。

## 哈希表

哈希表通过哈希函数 H(key) 把关键字直接映射到存储位置，理想情况下查找、插入、删除均为 **O(1)**。

常见哈希函数构造方法：

- **除留余数法**：H(key) = key mod p，p 通常取小于表长的最大质数，避免关键字聚集；
- **直接定址法**：H(key) = a·key + b，适合关键字连续分布；
- **数字分析法、平方取中法、折叠法**：适合关键字位数较多的场景。

冲突（collision）不可避免（鸽巢原理），处理方法分两大类：

**开放定址法**（所有元素都存放在表内）：

- 线性探测：冲突后依次探测下一个位置。简单但会产生**一次聚集**，冲突元素连成一片，降低效率。
- 平方探测（二次探测）：探测序列为 +1²、−1²、+2²、−2²……可缓解一次聚集，但**表长必须是 4k+3 形式的质数**才能保证探测到全表。
- 双散列：用第二个哈希函数决定步长，聚集最轻。

开放定址法**删除元素不能直接置空**，否则会截断后续元素的探测链，必须使用「墓碑标记」（已删除但可复用）。

**链地址法（拉链法）**：每个槽位挂一个链表（或红黑树）。冲突元素放入同一链表，删除简单，装填因子可以大于 1。Java HashMap 正是这种结构，并在链表长度超过 8 且表长 ≥ 64 时转为红黑树，把最坏查找从 O(n) 降为 O(log n)。

**装填因子** α = 表中记录数 / 表长。α 越大冲突越多、ASL 越大。开放定址法一般控制 α ≤ 0.75，链地址法可放宽到 1 以上。哈希表的**平均** ASL 只与 α 有关，与表长 n 无关，这是它区别于其他查找结构的关键性质；但**最坏**情况（所有 key 冲突）仍是 O(n)。

## 常见错误

1. **二分查找用在中序链表上**：链表不支持 O(1) 随机访问，二分没有意义，复杂度会退化为 O(n log n)。
2. **二分边界条件混用**，造成死循环。
3. **哈希表用开放定址法时直接删除元素**，导致后续查找失败。
4. **哈希函数取模用合数**（如 2 的幂），低位分布不均造成大量冲突；Java HashMap 用 `(n-1) & hash` 并配合扰动函数也是出于分布考虑。
5. **把哈希表的 O(1) 当成最坏情况**：哈希碰撞攻击（HashDoS）可使性能退化到 O(n)。
6. **认为 α 越大越好**：空间省了但冲突剧增，应结合场景在 0.5~0.75 之间取平衡。
7. **在需要范围查询的场景用哈希表**：哈希表不支持有序遍历与区间查询，这类需求应使用 B+ 树或跳表（如 Redis 的 zset）。
